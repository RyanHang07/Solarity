## 1. Three error surfaces no spec can see

**The strongest finding, because the code already knows and says so.**

`e2e/ui.ts` locates every error as `p[role="alert"]` with non-space text. That
tag is deliberate — it steps around Next's dev overlay, which mounts its own
empty `alert` node on every page, and whose second failure mode is the dangerous
one: exactly one node matches, `textContent()` returns `""` immediately, and the
assertion fails with "no error shown" while the screenshot shows the error
plainly there.

The design port then introduced **three alerts that are not `<p>`**:

| File | Line | Element |
|---|---|---|
| `app/(app)/circles/[id]/report-checkin.tsx` | 124 | `<span role="alert">` |
| `app/(app)/circles/[id]/today-roster.tsx` | 301 | `<li role="alert">` |
| `app/(app)/(shell)/dashboard/photo-button.tsx` | 198 | `<span role="alert">` |

Each was a correct HTML decision — a `<p>` inside a `<form>`'s phrasing context
or inside a `<ul>` is invalid nesting. Each carries a comment acknowledging that
`e2e/ui.ts` cannot see it. `photo-button.tsx:194` goes furthest and states the
consequence outright: *"Nothing asserts on either today."*

**So three error paths — a failed check-in report, a roster failure, a failed
photo upload — cannot be asserted on by the project's own helper.** They are not
untested by oversight; they are untestable by construction, and the construction
was documented three times without being fixed.

This is the pattern `docs/testing.md` already names twice: **a comment stating
the right diagnosis is not evidence the code implements it.** Third instance.

**✅ Applied.** `e2e/ui.ts` now reads:

```ts
return scope.locator(':is(p, span, li)[role="alert"]').filter({ hasText: /\S/ })
```

The emptiness filter is what actually defeats the dev overlay — the tag was only
ever a second line of defence, and it had cost more than it saved. `FormError`'s
comment in `components/ui/field.tsx` was corrected, since it told the next person
that a non-`<p>` alert "would match nothing", which is no longer true, and all
three site comments were rewritten from "known gap" to the rule: **choose the
element the parent permits and add the tag to the helper, never the reverse.**

`report-checkin.tsx` went further and now uses `FormError` outright — a `<p>` was
always legal there (its parent is a `<form>`, not phrasing content), and it had
been a hand-rolled `<span>` *only to match `photo-button.tsx`*. A special case
kept alive to resemble another special case is worth deleting.

**✅ All three now asserted**, and writing them turned up something bigger than
the finding.

| Path | Where | How it is made to fail |
|---|---|---|
| Photo refused | `photos.spec.ts` | A buffer declared `image/png` whose bytes are text. `inspect()` sniffs the leading bytes and ignores both filename and MIME, so this proves the sniffing rather than an extension check — and it is client-side, so it costs no round trip, no object and no token |
| Roster share refused | `roster.spec.ts` | The hidden `entryId` overwritten with a UUID that is not yours. `setNoteSharing` scopes by RLS rather than by what the form claims, so the update touches nothing and the action returns a sentence. Proves the scoping *and* the surface |
| Report refused | `roster.spec.ts` | The hidden `contentType` overwritten with a value outside the allow-list |

**The larger finding: nothing opened the report form at all.** Chasing the
error surface revealed that the whole report-a-note flow — the control, the
panel, the submit, the "Reported. Thanks." replacement, the row in
`content_reports` — had no UI test. The refusal was untestable because of the
locator; the *success* was untested for no reason but oversight. Both are
covered now.

**One branch deliberately left unasserted.** The textarea's `maxLength` is 500
and `REASON_MAX` is 500, so a reason the server would refuse for length cannot
be produced from the UI. That is the right arrangement, and a test that forced
it would assert on a state the app cannot enter.

Each new assertion also checks that **the refusal wrote nothing** — a refused
toggle leaves `note_shared` as it was, a refused report leaves no row. An error
message shown over a write that happened anyway is the worse bug and the one an
error-surface test is uniquely placed to catch.

## 2. No `error.tsx` anywhere in the app

There is no `error.tsx` and no `global-error.tsx` in the repository. Confirmed
by glob across `app/**`.

Every route therefore falls back to Next's built-in error boundary when a server
component throws. In production that is an unstyled page with no `.ds-app`, no
type scale, no wordmark, and **no way back into the app** — on a phone installed
to the home screen, where there is no browser chrome, that is a dead end.

This matters more here than in most apps for two reasons:

- **`.ds-app` is only on the app shell.** A page rendered outside the layout
  gets the root 16px and none of the palette. The two `not-found.tsx` files were
  written precisely because of this; the error case was missed.
- **Every page in `(app)` is a server component doing Supabase reads.** A
  network blip, an expired session mid-render, or a PostgREST schema cache
  serving a stale shape — all three have happened in this project — surface here.

**✅ Applied.** `app/(app)/error.tsx` inside the route group, so it renders within
that group's layout and keeps the nav — the same reasoning as
`app/(app)/not-found.tsx`. `app/error.tsx` wraps itself in `AuthShell`, because
the public routes have no other source of `ds-app`.

Two decisions worth keeping:

- **Neither shows `error.message`.** A server throw here is a Supabase or
  PostgREST failure, and those carry column names, constraint names and
  sometimes a fragment of the query — a schema disclosure on a page anyone can
  reach by breaking one request, and unreadable to the person seeing it.
  `error.digest` is the safe identifier: Next replaces the message with a hash in
  production and logs the real one server-side, so it is exactly what a support
  email should quote. Rendered only when present, since an empty reference line
  reads as a bug in the error page itself.
- **The signed-out one offers home, not "back".** `/dashboard` would bounce off
  the gate and land on sign-in having lost the error.

`app/global-error.tsx` is deliberately not added: it replaces the root layout,
must ship its own `<html>`, and only catches throws in the layout itself — which
has no logic that can throw today.

## 3. `sign-up.spec.ts` spends the two tightest IP-keyed limits and clears none

**Corrected after counting. The first draft of this finding named four specs and
two of them spend nothing** — the correction is kept because the wrong version
is the more instructive one.

Twelve specs call `clearRateLimits()`. `sign-up.spec.ts` is not one of them, and
counting actual submissions rather than tests:

| Limit | Budget | Spent per run |
|---|---|---|
| `signUp` | 10 / hour, keyed by IP | **5** (lines 52, 110, 158, 357, 511) |
| `passwordReset` | 5 / hour, keyed by IP | **2** (lines 444, 450) |

**Two runs inside an hour exhaust both**, before Playwright retries are counted,
and `lib/ratelimit.ts:174` records that localhost sends no `x-forwarded-for`, so
every local request shares one IP bucket. This is the shape of the bug already
documented: runs degrading across an hour with no code change.

**What the first draft got wrong, and why it matters.** It claimed the two
address-keyed limits (`resendConfirmation` and `passwordResetAddress`, 3/hour
each) were the tightest exposure. They are not: `freshEmail()` is unique per
run, so those see a new key every time. The one fixed-address call is in "asking
for a reset says the same thing for any address" — a test deliberately built to
pass whether or not it is refused, because the action swallows a rate-limit
refusal precisely so a limit cannot leak which addresses exist. **The tightest
number in the table was the safest one**, because the code around it was
designed for it.

Two more specs were named and clear themselves:

- **`delete-account.spec.ts` spends nothing.** Line 87: *"And then we do not
  press it."* The test drives the confirmation gate to the point of enabling the
  button and stops, with a post-hoc assertion that the account still exists.
- **`photos.spec.ts` spends one token** against `photoUpload` (20/hour), on a
  single `setInputFiles` at line 396. Most of the file is API-level, and
  `enforce` only runs inside server actions.

**Applied:** `beforeAll(clearRateLimits)` in `sign-up.spec.ts` (a live exposure)
and `goals.spec.ts` (4 of 20 `createGoal` per run — insurance, not a fix). The
other two were left alone, because a guard that buys nothing teaches the next
person that this call is boilerplate.

**Still worth doing:** the comment in `db.ts:117` claiming per-file calls has now
been wrong twice. A Playwright project dependency would make it structural
rather than remembered.

## 4. The hydration guard exists in one spec, the pattern in eighteen places

`moderation.spec.ts:106` carries the diagnosis and the only guard in the suite:
a `<form action={fn}>` in a **client** component has a placeholder `action`
attribute until React attaches, so a click on a visible, enabled submit button
does nothing — no error, no network request, no failure until a later assertion
times out somewhere unrelated.

Eighteen client components render such a form. `profile-actions.tsx` is guarded.
The rest are not:

`join-button.tsx`, `avatar-form.tsx`, `blocked-list.tsx`, `accept-form.tsx`,
`onboarding-form.tsx`, `delete-account-panel.tsx`, `report-checkin.tsx`,
`today-roster.tsx`, `sign-up-form.tsx`, `password-form.tsx`, `reset-form.tsx`,
`forgot-form.tsx`, `resend-form.tsx`, `first-goal-form.tsx`,
`streak-decision.tsx`, `goals-panel.tsx` (four forms), `role-form.tsx` (two),
`invite-panel.tsx` (three), `archive-panel.tsx`.

**Forms in server components are not at risk** — `app/(app)/layout.tsx:192`,
`today/page.tsx:99`, `sign-up/page.tsx:52` and `check-email/page.tsx:121`
receive a real `action` attribute and submit without JS. The distinction is the
whole diagnosis and is worth keeping explicit.

Most specs assert something before clicking, which incidentally proves
hydration. That is luck, not design, and it is why this is Medium rather than
High: the suite is green, and the failure mode is intermittent and misattributed
when it does occur — three wrong diagnoses last time before the user's own
observation settled it.

**✅ `submitAndWait` added to `e2e/ui.ts`** and used by the new settings test.
Not retrofitted across the eighteen: the suite is green, so a sweeping rewrite
of working specs would risk more than it fixes. Adopt it where a spec is being
edited anyway.

Two details the helper's comment argues for, both learned the hard way:

- **It waits on the POST, not on the effect.** Asserting on what the action
  changed reports the *consequence* as missing rather than the request as never
  sent — which is precisely the misdirection that cost four wrong diagnoses.
- **It asserts `toBeEnabled()`, not `toBeVisible()`.** A `useFormStatus` submit
  is disabled while a previous submission is in flight, and clicking a disabled
  button is a silent no-op that reproduces the very bug the helper prevents.

## 5. Two settings toggles have no test that drives them

**Substantially corrected. The first draft named eleven actions and at least
four of them are well tested** — the method was wrong, and the way it was wrong
is worth more than the list.

I grepped the specs for action names and for UI strings I guessed at. Action
names never appear in e2e, because specs drive the UI; and the strings I guessed
were not the strings in the code. "Hide everywhere" returned nothing, so
`setHiddenEverywhere` looked untested. The real label is **"Hide from every
Circle"**, and `roster.spec.ts:760` drives it, toggles it back at :786, and
asserts at :774 that a hidden goal never reached a circle-mate. Likewise
`setNoteSharing` is driven at `roster.spec.ts:333`, `blockedAccounts` via
`moderation.spec.ts:188`, and `updateTodayScreenMode` at `dashboard.spec.ts:482`.

**A grep that misses is indistinguishable from a gap.** The fix was to find each
action's *form* and locate it by the `aria-label` the markup actually carries —
`settings-forms.tsx` gives each one a stable name for exactly this purpose.

Done that way, two remain, both in settings:

| Action | Form `aria-label` | Why it matters |
|---|---|---|
| `updateStatsVisibility` | `Profile stats` | Whether four lifetime numbers show on your public profile |
| `updatePushShowsCircleName` | `Notification detail` | Whether a Circle's name appears on your lock screen |

**And the shape of this gap is the interesting part.** `profile.spec.ts` covers
what stats visibility *does*, thoroughly — withheld stats are not rendered as
zeroes, your own always show you, a stranger's are opt-in. But it sets the flag
with an admin write at line 52. **The consequence was proven and the control was
not**: `updateStatsVisibility` could write the wrong column, misread an unticked
checkbox, or fail silently, and every assertion in that file would stay green
while the toggle in settings did nothing.

**✅ Both now tested**, in `dashboard.spec.ts` beside the check-in-screen test.
The assertion is on the stored value rather than on the profile, because
re-checking the profile would re-test `profile.spec.ts`'s subject; the only new
claim is that the form writes what it says it writes. Both directions, because
a checkbox sends nothing when unticked — the actions read absence as off, which
is correct and is also the half a one-directional test would miss.

**✅ `exportUserData` now tested too**, in `delete-account.spec.ts`. The
assertions are `/support`'s own sentences, in both directions — the seven keys
it promises are present, and the four it says are absent (notifications, push
devices, blocks, reports) are absent, plus no `@` anywhere in the profile block.

**The negative half is the one worth having.** This project has run two
legal-accuracy passes and the second found that step 20 had falsified both
policy pages without anyone noticing. A promise about what a file *omits* rots
silently: adding a key to `export_user_data` is a one-line change that makes a
published sentence false, and nothing else in the repository would notice.

Lower value, still unverified either way: `revokeInviteLink` — `boundaries
.spec.ts:263` defers it with *"`INVITE_REVOKED` is covered by the UI suite"*,
and whether that is still true was not checked.

## 9. The data export had never worked — migration 113

**The only finding in this audit that was a live defect rather than a gap**, and
it was found by writing the test from finding 5, which failed on its first run.

`export_user_data()` is `security invoker`. `authenticated` has **no SELECT
grant on `public.users`** — the only one of the export's eight tables without
it, because profile reads go through masked `security definer` RPCs. A
security-invoker function cannot read a table its caller cannot read, so it
raised `42501` on its first block, for every user, always.

**Two decisions collided, and each was right on its own.** `users` is withheld
so nothing can read it unmasked; the export was written invoker-side so it is
"structurally incapable of returning anyone else's rows even if a WHERE clause
were wrong". Together they produce a feature that cannot run.

**Why it survived.** `lib/errors.ts` renders a bare 42501 as "You don't have
access to that." — which is also what the function's own null-`auth.uid()`
guard produces. One sentence for two unrelated causes, so even someone who hit
it would have gone looking at their session. And nothing called it:
`delete-account.spec.ts` asserted the link was *visible* and stopped.

**Fixed as `security definer`**, proven in a rolled-back transaction in both
directions before anything was applied — a real user gets their own seven-key
export, a second user gets only theirs, a caller with no uid is refused — then
applied with those assertions inline. The alternative, granting `authenticated`
SELECT on `users`, would undo the masking model across the whole app to fix one
function.

**The general lesson, which is the same one this audit keeps producing:** an
error message that collapses two causes into one sentence is a debugging trap,
and a feature nothing calls is a feature nobody knows is broken. *"A broken
export is discovered by someone already trying to leave"* was written in this
document as a reason to test it. It was already true.

## 8. Two export paths, and only one is reachable

**Found while testing finding 5's leftover.** The export exists twice:

- `app/(app)/settings/export/route.ts` — the route handler the UI links to,
  calling `exportUserData()` and stamping `solarity-YYYY-MM-DD.json`
- `supabase/functions/export-data/index.ts` — an Edge Function calling the same
  `export_user_data` RPC, stamping `solarity-export-YYYY-MM-DD.json`

Nothing in the app links to the second. Both are `security invoker`, so neither
is a privilege problem, and the duplication is not currently a bug — but it is
two implementations of a published promise, with different filenames, and only
one is exercised by anything. If the Edge Function is dead, delete it; if it is
the documented API, say so somewhere.

Not investigated further. Recorded so it is a decision rather than a discovery
made twice.

## 7. `/join/[token]` has no loading state

`loading.tsx` exists at `app/(app)/`, `app/(app)/(shell)/` and
`app/(app)/(shell)/dashboard/`. The `(app)` one covers every signed-in route by
the nearest-ancestor rule, so coverage there is fine.

Outside it, only `/join/[token]` does real work before rendering — a token
lookup and a member preview — and it is the **first page a new person ever
sees**, often on a phone on mobile data, arriving from a message. A blank screen
there reads as a broken link.

`/auth/*`, `/onboarding/*` and the legal pages need nothing.

**Tried, and reverted. The fix was worse than the gap**, and the way it failed is
the most useful thing in this document.

`app/join/[token]/loading.tsx` was added, wrapped in `AuthShell wordmark`. The
suite went red in two places, both of them this file:

**1. A `loading.tsx` turns a server redirect into a client navigation.**
`page.tsx:106` calls `redirect("/?notice=invite-invalid")` for a dead token.
With no loading file, the page component runs before a single byte is sent, so
Next answers with a plain HTTP redirect. **With one, the route streams**: the
shell flushes immediately as a 200, the page resolves afterwards, and the
redirect arrives in the RSC payload as a client-side navigation.
`rate-limit.spec.ts` reported it as *"Navigation to /join/probe-token-2 is
interrupted by another navigation to /?notice=invite-invalid"*, which is a
precise description of a thing nobody had intended.

For a person, that is a skeleton flashing and then a bounce, where before there
was a clean redirect. Worse than no loading state.

**2. It widens the hydration window on the one screen that cannot afford it.**
`join-button.tsx:51` is `<form action={action}>` in a client component. Painting
a shell first means the button is visible and enabled earlier relative to
hydration, so a click can land on a form whose `action` is still a placeholder
and do nothing at all. `streak-decision.spec.ts` caught it as a URL that never
changed after pressing Join.

**This is finding 4 arriving as a live defect rather than a test gap**, on the
first page a new person ever sees, reached from a message, usually on mobile
data. The population most likely to hit the race is exactly the population the
loading state was meant to help.

**The lesson generalises past this route:** `loading.tsx` is not a free
addition. On any route whose page can `redirect()`, or that carries a
client-component form, it changes *when* things happen, and both changes are
invisible until something races.

Keeping it would mean moving the token lookup ahead of the stream, or the
redirect into the proxy. That is real work for a finding rated Low, and it is
not the sort of thing to do in the hour before a push. Recorded here so the next
person reaches for it knowing the cost.
